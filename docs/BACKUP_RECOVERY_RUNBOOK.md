# Backup and recovery runbook

Stage 7 Phase A, **10 November 2026**. No live Atlas settings, data, credentials, snapshots, access lists or recovery jobs were changed. The owner has not supplied a verified Atlas tier, backup policy, last recovery point or restore record. **Automated backups and point-in-time recovery are unverified, not assumed enabled.**

## Proposed objectives and approval inputs

Propose **RPO ≤1 hour** (maximum acceptable lost writes) and **RTO ≤4 hours** (incident declaration to validated service restoration). These are approval targets, not achieved commitments. They cannot be accepted until available Atlas capability, encrypted key escrow, operator access, cost and a timed isolated drill demonstrate them. If the current tier cannot meet the target, the owner must choose an approved upgrade/backup method or explicitly different objectives before release.

Proposed recovery-point retention: hourly 48 hours, daily 30 days, monthly 12 months; this is a discussion starting point, **not a configured policy or a health-record retention recommendation**. The owner must reconcile storage cost, clinical-record retention/deletion obligations, regional copies and approved data locations. A backup is not the application record-retention policy.

[Atlas Cloud Backup](https://www.mongodb.com/docs/atlas/backup/cloud-backup/overview/) distinguishes dedicated M10+ from Flex/Free capability, supports separate regional distribution and requires suitable project backup access. Follow the documentation for the **actual** tier. Do not infer PITR from the existence of a snapshot. Record the last recoverable timestamp, retention window, restore limits, region and applicable account permissions in a restricted operations record. Enabling paid backups, changing tier or policy needs explicit authorization.

| Asset                      | Protection and recovery requirement                                                                                                                                                                                                                      |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Atlas documents/indexes    | Approved snapshots/PITR or a separately reviewed logical backup; encrypted protected destination, schedule/failure alerts, tier/version/topology compatibility, isolated restore drill. Never export clinical data into this public repository or CI.    |
| Current MFA encryption key | Separate recoverable escrow in owner-controlled encrypted vault with restricted audited access; preserve relevant versions for the backup window. A database snapshot alone cannot decrypt MFA. Verify availability without copying the key to a report. |
| JWT/CSRF/DB credentials    | Restricted vault; incident-specific revocation/rotation plan. Restored authentication state must be deliberately invalidated before exposing the recovered service. Do not rotate the MFA key blindly.                                                   |
| Source/built releases      | Exact approved full SHA, source/archive/lockfile checksums, build versions/origins, built-output hash inventory and prior compatible artifact; no runtime secrets. Retain current and at least one known-good release.                                   |
| Host/Caddy state           | Proposed daily VM backups protect OS/configuration/certificate state; access must account for root env files included in host snapshots. Confirm encryption, backup readers and restoration rights. **Host backup does not back up remote Atlas.**       |
| DNS/operational access     | Owner recovery contacts, registrar/provider MFA, zone inventory, break-glass procedure and named incident/restore approvers. Store privately; no passwords or recovery codes in Git.                                                                     |

Backup operator: **unassigned**. Incident owner: **unassigned**. Restore approval: repository owner plus the approved data operator. Periodic proposal: inspect backup health daily, test restore monthly and after key/tier/topology changes, subject to approved policy. Alert delivery and durable encryption/key recovery remain live gates.

## Safe isolated restoration after authorization

1. Declare the incident, record time, assign operator/approver and preserve sanitized evidence. Decide whether it is a failed release, outage, accidental deletion, corruption or compromise. A failed application release normally needs code rollback, **not** data restoration.
2. Identify the exact source cluster/database and desired recovery timestamp privately. Confirm the latest valid backup, data-loss interval, version/topology compatibility and available MFA key. Verify the destination is a **new isolated cluster/database** with restricted networking and no public app traffic. Record target identity twice before proceeding.
3. Restore the approved Atlas snapshot/PITR to that new destination using authorized project backup access. For a logical tool alternative, use compatible [MongoDB Database Tools](https://www.mongodb.com/docs/database-tools/mongorestore/), a reviewed encrypted artifact, explicit target namespaces and private credential injection. Do not put connection strings on a shared command line/history, restore over production or use destructive/drop flags as a shortcut. No production URI or destructive restore command is supplied here.
4. Verify collections, indexes, document counts, representative IDs, doctor/patient relationships, BSON types, timestamps and encrypted MFA readability. Validate permissions and verified TLS. Store only counts/check outcomes in the incident report; keep any clinical examination within authorized tooling.
5. Revoke restored sessions and outstanding challenges under a separately reviewed incident procedure before allowing traffic, so old restored tokens cannot regain authority. Test password + actual TOTP/recovery with a controlled authorized account against the isolated destination. Preserve existing encrypted secrets; do not disable MFA to make restore appear successful.
6. Verify authorized reads and separately approved test writes, analytics, readiness and failure handling. Measure recovery-point gap and **total** time including provisioning, data restore, keys, network, application rebuild/start, validation and owner decision. Compare to approved RPO/RTO; document failure honestly and keep production untouched if validation fails.
7. Obtain explicit cutover approval, then use the single-API maintenance release process with reviewed configuration. Preserve the original source/backup for investigation. Watch errors/resources, confirm reconciliation and record actual incident closure. No automatic cutover or database replacement script is shipped.

Accidental deletion may require selective recovery from an isolated copy, with authorization and relationship reconciliation, rather than whole-database replacement that discards later valid writes. Credential compromise additionally requires credential/session revocation, forensic evidence and key exposure assessment. Follow [security rotation](SECURITY.md#secret-rotation); ordinary release rollback does not rotate keys or rewind records.

## Evidence shipped in the repository

`npm run test:infrastructure` executes the full operational rehearsal through pinned Caddy. It creates its own temporary replica set, CA/certificate and fixture keys, and constructs all API database URIs internally. It snapshots BSON and index metadata in memory, deletes one **fixture** patient, restores to a second fixture database, checks IDs/relationships/indexes, decrypts preserved MFA and performs actual restored-account recovery login. It also disconnects/reconnects the fixture database and verifies readiness recovery. No API `.env` or external database URI is loaded.

This is **partial application-level recovery evidence**. It does not exercise an encrypted durable backup, Atlas snapshots/PITR, Database Tools, cloud permissions, real region failure or a measured production RPO/RTO. The Next process performs normal web env loading with explicit fixture origins; files remain unchanged. Temporary private certificates are removed. Resource samples contain numeric metadata only.

Before production, attach a restricted evidence record containing: target identity, chosen backup and timestamp, encryption/key access confirmation, operator, start/end times, measured RPO/RTO, counts/integrity/auth checks, failures and approval. Do not attach patient payloads, credentials, invitations or recovery codes. A green CI rehearsal cannot close this production gate.

## Failed release rollback

Use [the deployment runbook](PRODUCTION_DEPLOYMENT_RUNBOOK.md#serialized-native-release-and-rollback) to stop the failed services, select the previous verified code/build with matching non-secret origins and preserved current secret configuration, then start **one** API and run smoke checks. No schema/data migration is introduced in Stage 7, so normal rollback keeps the database in place. If a later release changes schema/key compatibility, it requires its own reviewed reversible migration and recovery plan. A source SHA alone is insufficient if its matching build/runtime configuration is lost.
