# Stage 5 quality audit

Audited 9 November 2026, starting from `3695d35f95505be559671936b39c11227a143722` on `main`. This is an implementation and local verification record, not a security, clinical or accessibility certification. Stage 6 deployment was not performed.

## Scope and baseline

The initial working tree was clean and the selected public remote was `akonBRO/doctor_tracker`. The review covered README, implementation/security/doctor/patient/dashboard/design documentation, all App Router pages, shared form/navigation/query components, Express middleware/routes/services, authentication/session rotation, models/indexes, build configuration, tests, CI and rendered screens. The original PDF remains the assignment specification; the owner's Stage 5 request controls this work.

Before performance changes, the original **204 API tests** passed and a production build passed. Six baseline browser checks covered auth/CRUD/dashboard at 1440 and 320px. The quality harness then captured the unchanged application with a disposable 200-doctor/4,000-patient replica-set fixture. Existing environment files, Atlas configuration, administrator accounts and persistent records were not modified or used for test fixtures.

The approved white/sky-blue design, logo geometry, page composition, typography sizes and clinical field contracts were retained. Findings drove the following limited changes.

## Bangladesh data review

- Existing Unicode/NFKC names accept Bengali and English, including doctor titles; hospital names remain free text, not a small fixed list.
- `01712345678` and `+8801712345678` normalize through the existing Bangladesh mobile policy. Valid supported hospital landlines/international contacts and existing stored formats remain readable. Validation does not prove phone ownership/reachability.
- Eight divisions and 64 districts are validated using the existing supported data; district options depend on division and changing it clears dependent values. Upazila/thana remains validated free text, not a claimed complete national lookup.
- All eight ABO/Rh values and Unknown remain valid. Unknown history/allergies do not become confirmed negative findings. Approximate age does not fabricate a DOB.
- New-record requirements and sparse legacy PATCH semantics are unchanged. No new sensitive fields, NID requirement, invented medical values, backfill or persistent-data migration was added.
- Record displays use day-first Asia/Dhaka formatting. ISO API timestamps, directory creation-date filters and registration buckets use their existing explicitly labeled UTC semantics.
- The full Bengali font remains local under its license; no remote font request is introduced. Expanded Bengali name/address fields are exercised by real browser/API fixtures.

## Measurement method and before/after results

Reproduce with the test origins from README, a production build, then:

```powershell
$env:QUALITY_PHASE = 'after'
node scripts/test-e2e.mjs tests/e2e/quality.spec.ts --project=desktop
```

The runner rejects occupied fixture ports, uses a disposable MongoDB replica set and verifies its own API process identity. The quality test enrolls an actual administrator, keeps cookie state only in process memory, seeds **200 doctors / 4,000 patients**, then records metrics without saving identities, cookies or record payloads. Output is ignored `tmp/quality/after.json`; the reviewed sanitized before/after evidence is committed in [quality-metrics.json](quality-metrics.json). Baseline application source was the starting commit; the profiling harness itself was new.

The empty dashboard is measured before fixture insertion; all populated page/API samples use the 200/4,000 fixture. Request counts refer to browser-issued API calls and exclude server-rendering authentication checks.

Local environment: Windows, Node 22.16.0, Chromium 158.0.8127.18, loopback production Next/Express, no network/CPU throttling. Each page has three fresh browser-context samples against a warm server/database. Each endpoint has five sequential HTTP samples. Page-ready means the test's visible data plus **500ms network-idle stabilization**; it is not TTI, a Core Web Vitals field result or a Lighthouse score. Resource Timing counts decoded/transfer JS, font transfer, FCP and layout shifts; CDP Performance measures accumulated script execution. Three samples are a small lab observation, not a statistical performance guarantee.

## Database, pagination and freshness decisions

Doctor/patient list services retain projected lean reads, bounded parallel find/count queries, validated scalar filters, escaped token prefixes, deterministic `_id` tie breakers and 3-second query budgets. Details use the existing `_id` index. Suggestions use bounded aggregation. Page size is bounded server-side; search debounces 300ms, resets page one, cancels obsolete requests and preserves meaningful URL state. No browser full-dataset filtering was introduced.

Final representative `explain('executionStats')` winning plans from the quality fixture:

| Query                              | Index                                                   | Keys / documents examined / returned |
| ---------------------------------- | ------------------------------------------------------- | ------------------------------------ |
| Doctor newest                      | `createdAt_-1__id_-1`                                   | 10 / 10 / 10                         |
| Specialization + hospital + newest | `specializationKey_1_hospitalKey_1_createdAt_-1__id_-1` | 10 / 10 / 10                         |
| Selective doctor token prefix      | `searchTokens_1`                                        | 2 / 1 / 1                            |
| Patient newest                     | `createdAt_-1__id_-1`                                   | 10 / 10 / 10                         |
| Patient doctor + condition         | `doctorId_1_conditionKey_1_createdAt_-1__id_-1`         | 10 / 10 / 10                         |
| Selective patient token prefix     | `searchTokens_1`                                        | 2 / 1 / 1                            |
| Patient offset 2,990, limit 10     | `createdAt_-1__id_-1`                                   | 3,000 / 10 / 10                      |

The same baseline cases had the same keys/documents/return counts. The original collector included rejected-plan index names; the final collector visits only the winning plan, and baseline index names are deliberately omitted from the archived comparison. No index was added or removed: fixture usage is not enough evidence to declare an index unused in real traffic. Existing individual/combined date/filter/name/token indexes continue to serve the established routes.

The retained dashboard integration workload separately verifies 200 doctors/4,000 patients: exact totals use `_id_`; assignment lookup uses the `doctorId` compound prefix without fetching patient documents; date aggregation uses the creation-date index without fetching source documents. See [Dashboard Analytics](DASHBOARD_ANALYTICS.md) for the original plan observations and exact pipeline definitions. Distribution performs one server-side aggregate with count lookups, not application N+1 requests; global ranking still scales with the whole doctor/assignment population. Node merges at most 90 date buckets, not full source records.

**Offset pagination retained:** page 300 examined 3,000 index keys but only ten documents and completed in ~13ms HTTP locally. Growing offset cost is real; cursor pagination would change random-page/URL/total UX without a demonstrated assignment benefit. Review with actual volumes, search selectivity and latency before Stage 6 scaling. No larger fixture was needed to establish the two demonstrated asset reductions; this does not prove larger-scale capacity.

**Freshness retained:** no-store API/client reads, no persistent browser/analytics cache, concurrent independent dashboard datasets, entry/manual/mutation refresh and at most once-per-minute visible-tab/focus revalidation. Different filter/period keys hide previous data; stale responses cannot overwrite new keys. Logout leaves protected mounted state and invalidates the server session. Cross-tab/operator changes appear on re-entry/focus/manual/visible refresh; there is no real-time consistency promise. Exact counts and independent datasets are not a transactional snapshot.

## Accessibility review

Automated checks now include `wcag2a`, `wcag2aa`, `wcag21aa` and `wcag22aa` tags. The full five-width suite checks real public/auth/record/dashboard states. The larger-fixture quality pass additionally checks dashboard, patient directory and edit at 320px. No axe violations were found in those final checked states; the baseline subset also had no violations, despite the separately reproduced picker focus defect.

Keyboard checks include skip-to-content, visible focus, mobile menu focus/Escape return, form validation, modal dismissal/confirmation, picker selection/Escape and chart/table access. Controls retain existing readable sizes, native labels/selects, semantic table headings, reduced-motion handling and restrained contrast. The [WCAG 2.2 target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) includes size and spacing exceptions; small inline text links were not indiscriminately enlarged. Dynamic chart data retains its full daily-count text alternative. Bengali font conversion preserves shaping tables and all glyphs.

No screen-reader hardware/session, physical touch device, alternate browser engine or formal WCAG conformance audit was performed. Automated axe results cover the selected states and rules only. Visual review is recorded with the screenshot matrix in [Design Redesign](DESIGN_REDESIGN.md), plus the dashboard state matrix in [Dashboard Analytics](DASHBOARD_ANALYTICS.md).
