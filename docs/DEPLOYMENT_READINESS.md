# Stage 6 deployment readiness

Stage 5 has completed local quality work. **No deployment has been performed.** This is the deployment contract for the existing standalone Next.js frontend, Express API and MongoDB replica set; it is not approval to store real patient data or a claim of production security certification.

## Required configuration

Use a secret manager for API secrets. Never copy local `.env` files, invitation links, recovery codes or patient records into build artifacts, repositories or shared logs. Variable names and public examples are in the committed `.env.example` files; this document intentionally contains no actual values.

## Host and edge requirements

- Restrict inbound access to the intended public entry point; keep database and direct API endpoints off public bypass paths. Review outbound access and deployment/secret-manager permissions.
- Align edge body limits with existing 16KiB ordinary / 64KiB patient JSON limits. Set deliberate header/body/idle/upstream timeouts and connection/rate protections at the edge. The browser's 15-second per-request deadline is not slow-client/DDoS protection.
- Verify production nonce CSP, HTTPS redirects, HSTS scope, frame/MIME/referrer protections and Secure/HttpOnly/Strict host-only cookies (production names use `__Host-`). Confirm no proxy rewrites cookie scope or caches authenticated pages/errors.
- Serve only intended web assets and API compiled output. Production browser/API source maps are disabled; verify actual hosted files. The source repository itself is intentionally public.
- Keep application and hosting logs free of credential/cookie/CSRF/MFA/invitation/clinical payloads. Application logs omit URLs and bodies; edge/access/error logs require separate review. Define retention, access and incident response.
- API health returns 200 only while Mongoose is connected and 503 otherwise. Use `/api/v1/health` for readiness with a sensible low-frequency probe budget; it shares the global limiter. Do not publish detailed database diagnostics.
- Startup awaits database connectivity/index initialization. The configured server-selection timeout is eight seconds; directory/analytics queries have three-second budgets. Known-disconnected requests now return sanitized 503 before buffering. In-flight outages can still reach existing driver bounds.
- API SIGINT/SIGTERM handling closes the HTTP server and MongoDB, with a ten-second exit ceiling in source. Verify termination/draining on the actual hosting OS; Windows browser tests are not evidence of Linux orchestration behavior.

## Before exposing a release

1. Run `npm ci`, typecheck, lint, format check, `npm test`, production build, the 15-check browser suite and the dedicated quality browser test. Run full and production-only dependency audits on the release lockfile. Keep successful CI for the exact release commit.
2. Exercise real HTTPS login, mandatory MFA, recovery, refresh across tabs, logout and protected-page rejection through the final domain/proxy. Verify cookies, CSRF, CORS, CSP, request budgets and real client IP. No local HTTP test establishes this.
3. Confirm the web build targets the intended API; test protected server rendering and browser rewrites against that same environment. Check empty/loading/error states rather than interpreting missing data as zero.
4. Use a controlled test workspace/database to check doctor creation/search/filter/page, patient create/edit/detail/scoped delete and dashboard totals/trends/distribution. Never seed fictional load fixtures in the owner's persistent clinical database.
5. Test database-unavailable responses and recovery, controlled API restart, graceful shutdown, edge timeouts, resource limits, monitoring/alerts and backup restoration. Confirm restored encrypted MFA data still works with the securely retained key.
6. Reassess actual data volume, latency and query plans. The Stage 5 200/4,000 local fixture is not a capacity/SLA guarantee. Offset cost grows; exact global ranking/counts are not constant-time. Add caching/cursors/indexes only with measured need and preserved authorization/freshness.
7. Define trusted invitation issuance and account-recovery procedures. No default user, public registration, email-delivery integration, password reset or MFA-reset endpoint is supplied. Keep one-time CLI invitations out of CI/public issues. Review operator access and key rotation/revocation procedures.
8. Approve applicable privacy, clinical-record handling, retention/deletion, backups, access and incident policies before real health data. All current administrators share a workspace; tenancy/per-record ownership is not implemented. Physical assistive-technology/browser testing remains an additional acceptance activity.

## Release and rollback

Keep the exact tested commit and lockfile plus origin configuration with the release record. This stage changes no database schema/index and requires no migration. Preserve the existing data and encryption keys across releases. Roll back application artifacts to a verified compatible version if needed; do not restore an old database blindly after live writes. Rotate/revoke credentials and sessions deliberately during incidents using the documented procedures.
