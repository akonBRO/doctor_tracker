# Implementation status

## Stage 3 - Patient Management and application redesign

Completed and locally verified 8 November 2026. Stage 3 delivers patient management and the full application redesign. Analytics and deployment are not included.

- Patient model: required international name, free-text condition and immutable indexed doctorId reference, plus timestamps and hidden normalized query fields. No embedded patient arrays or doctor/patient accounts.
- API: real scoped creation/list/removal, global listing/detail/edit/permanent deletion; strict allowlists; UTC creation-date ranges; Unicode word-prefix search; condition and doctor filters; stable sorts; bounded pages; exact filtered counts and one bounded doctor projection lookup per page.
- Integrity: existing parent checks; nested deletion matches both identifiers; assignments cannot be edited. Atomic update pipelines keep derived search state consistent and preserve disjoint concurrent changes. Atomic deletion returns 404 for a missing/concurrent loser and updates cannot resurrect records.
- Frontend: global Patients registry, real doctor lookup, patient detail and prefilled editor, doctor-specific creation/paginated lists/counts, irreversible delete confirmation. URL state, abort/debounce guards and no-store transport reuse the existing architecture. Forms keep drafts on errors, focus validation, prevent duplicate writes and never automatically replay mutations.
- Redesign: new typographic landing without the old diagram; single-column auth; graphite navigation; mineral-white surfaces; rust actions; readable inputs/labels/tables; structured mobile records. Original symbol geometry preserved across React/SVG/favicon; colors updated. Copy is reduced to tasks and real capabilities. Design rationale and before/after evidence are in DESIGN_REDESIGN.md.
- Security: JWT/MFA/database-session admin boundary, strict resource scopes, signed CSRF/exact Origin on POST/PATCH/DELETE, restricted CORS, unsafe-key/regex defenses, React escaping, nonce CSP, privacy-conscious logs and per-admin mutation limits. Existing auth controls and secrets are unchanged.
- Atlas: the existing ignored API environment/database configuration was retained. A read-only ping/topology check succeeded with automatic indexing and creation disabled. No records, accounts, invitations, sessions or MFA data were seeded, reset or modified for verification. All destructive test setup targets disposable test-server databases.

### Known boundaries and following stages

All administrators share one workspace; future tenancy must scope every query. Direct database operators must preserve doctor references because no doctor deletion endpoint exists. Same-field patient edits use last-writer semantics. Independent list/count reads are not a point-in-time snapshot. Offset pages/exact counts and token-filter sorting require workload-based evaluation in Stage 5. Search is prefix-based, not fuzzy or accent-insensitive. Explicit cancel/unload protects drafts; deliberate route navigation can discard them. Network-uncertain writes require inspecting the registry before resubmission; no idempotency keys are introduced.

Stage 4 can aggregate actual Patient doctorId, conditionKey and createdAt values for reporting; no analytics endpoints/charts or fabricated statistics are provided. Stage 5 performance refinements and Stage 6 deployment remain future work. HTTPS/proxy production checks, backup policy and multi-instance shared rate stores remain operational work. No deployment or doctor editing/deletion/reassignment, uploads, webhooks, email delivery, password reset or MFA reset is included.
